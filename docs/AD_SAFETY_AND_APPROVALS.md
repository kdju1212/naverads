# 광고비 안전장치·변경 승인 유지보수 노트

작성: 2026-11-01 · 갱신: 2026-11-02(브랜치 `feat/web-approval-security`, 마이그레이션 `0016_web_approval_locks.sql`) · 자료 확인일: 2026-11-01

로그인·세션·운영 보안 절차는 `docs/SECURITY_OPERATIONS.md`에 있다.

## 0. 한눈에

| 변경 | 누가 승인 | 서버 검사 |
|---|---|---|
| 캠페인 하루예산 **올리기**, 캠페인 **켜기**, 플레이스 **ADVoost 켜기** | **웹에 로그인한 사람이 `/approvals`에서** (Claude는 요청만) | 실행 직전 권한·변경 전 값·안전장치 재확인, 계정 잠금 |
| 입찰가 변경, 광고그룹·키워드·소재·확장소재 켜기, 키워드·광고그룹 등록, 소재·확장소재 등록, 제외검색어, 자동입찰 | Claude 허용 버튼(또는 웹 화면의 실행) | 같은 안전장치·계정 잠금 |

| 조회 | 없음 | 권한 검사 |

웹 승인 범위는 사용자 결정(2026-11-02)이다. "계정의 하루예산 설정액 합계를 늘릴 수 있는 변경"만 웹 승인 대상이다. 처음 요청은 "캠페인 예산 바꿀 때만"이었다. 꺼진 캠페인을 켜는 것도 합계를 늘리기 때문에 범위를 넓혔고, 사용자가 동의했다.

2026-11-02 2차 결정: **광고그룹 켜기는 웹 승인에서 뺐다**(사용자 요청). Claude 허용 버튼으로 실행되고, 실행 직전 안전장치(그룹·키워드·쇼핑 소재의 실제 입찰가 ≤ 클릭당 최대 입찰가, 그룹을 켠 뒤 하루예산 합계 ≤ 관리 기준, ADVoost 그룹은 캠페인 하루예산 필수)와 계정 잠금은 그대로 거친다.

## 1. 안전장치

조직·광고 계정마다 두 금액을 저장한다(`account_safety`). 같은 고객번호를 다른 조직이 연결하면 그 조직이 따로 정한다.
- **하루예산 관리 기준**: 켜진 캠페인들의 하루예산 설정액 합계가 넘으면 안 되는 금액.
- **클릭당 최대 입찰가**: 키워드·광고그룹·쇼핑 소재·플레이스 그룹 입찰가, 자동입찰·목표 ROAS 최대 입찰가의 상한. 켤 때 실제로 적용될 입찰가에도 쓴다.

설정은 관리자(OWNER·ADMIN)만 할 수 있다(`PUT /workspaces/{ws}/ad-accounts/{id}/safety`, `confirmed=true` 필요, `SAFETY_SET` 이력). 미설정 계정은 비용이 늘 수 있는 작업이 모두 막힌다.

### 합계 계산 (`safety.Snapshot.total`)
- 네이버의 지금 설정을 그 자리에서 읽는다(`GET /ncc/campaigns`, 필요하면 `GET /ncc/adgroups?nccCampaignId=`).
- 켜진(`userLock=false`) 캠페인만 센다.
  - 캠페인 예산이 있으면 그 값만 더한다.
  - 캠페인 예산이 없으면 켜진 광고그룹 예산의 합을 더한다. 이때 무제한인 그룹이 하나라도 있으면 계산할 수 없다.
- 계산할 수 없는 경우: 공유예산(`sharedBudgetId`), 무제한, 하루예산 없는 켜진 캠페인이 10개 초과(무료 플랜 호출 한도), 네이버 조회 실패.
- `useDailyBudget` 필드가 없으면 `dailyBudget` 값으로 판단한다. 예약·승인 작업의 변경 전 값 비교(`naver._check_expected`)도 같은 기준을 쓴다(11/02 맞춤).
- **입찰가 필드가 없거나 숫자가 아니면 0원으로 보지 않는다**(`safety._bid_of`, 쇼핑 소재는 `_ad_bid`). 비용이 늘 수 있는 작업은 "입찰가를 확인할 수 없어"로 막는다. 예산 필드가 없으면 무제한으로 보고 합계 계산 불가(막음).
- 캠페인 예산과 광고그룹 예산을 함께 쓸 때, 그리고 공유예산의 네이버 공식 동작은 공식 도움말에서 찾지 못했다(11/02 다시 검색). 그래서 캠페인 예산만 세고(그룹 예산은 그 안에 든다고 봄, 더 큰 값 기준이라 보수적), 공유예산은 막는다.

### 검사 규칙 (`safety.check`)
"비용이 늘 수 있는 작업"은 네이버를 다시 읽어 아래 두 가지를 본다. 둘 중 하나라도 판단할 수 없으면 실행하지 않는다.
- ① 실제 입찰가 ≤ 클릭당 최대 입찰가
- ② 변경 후 합계 ≤ 관리 기준

| 작업 | 검사 |
|---|---|
| 입찰가 변경(키워드·광고그룹·쇼핑 소재) | 상한. 네이버 지금 실제 입찰가(그룹 입찰가 상속 포함)보다 **올리면** 합계도 본다. 내리면 상한만 본다 |
| 새 입찰가(키워드·광고그룹 등록) | 상한 + 합계(키워드는 켜진 상태로 생긴다) |
| 키워드 켜기 | 실제 입찰가(`useGroupBidAmt`면 그룹 입찰가) ≤ 상한 + 합계 |
| 소재 켜기 | 쇼핑 소재는 자기 입찰가, 없으면 그룹 입찰가 ≤ 상한. ADVoost 그룹 소재는 아래 ADVoost 규칙 + 합계 |
| 광고그룹 켜기 | 그룹 입찰가, 켜진 키워드의 자기 입찰가, 켜진 쇼핑 소재 입찰가가 모두 ≤ 상한 + 합계(그 그룹을 켠 상태로 계산) |
| 캠페인 켜기 | 켜진 광고그룹마다 위 검사(10개 초과면 판단 불가) + 합계 |
| 캠페인 하루예산 올리기 | 합계(바꾼 값으로 계산). 줄이기·무제한→금액 설정은 검사하지 않음 |
| ADVoost 켜기(그룹 켜기 포함) | 캠페인에 하루예산이 있어야 함(없으면 막음) + 합계. 입찰가는 통제할 수 없다고 `uncontrolled`에 표시 |
| 확장소재 등록·켜기, 제외검색어 삭제 | 합계(확장소재는 켜진 상태로 생긴다) |
| 끄기, 예산 줄이기, 삭제, 제외검색어 추가, 조회 | 검사 없음 |
| 캠페인·광고그룹·소재 등록 | 꺼진 상태로 생긴다. 켤 때 검사. 입찰가 상한만 바로 본다(쇼핑 소재는 비우면 그룹 입찰가로) |

- 합계가 이미 관리 기준을 넘는 계정은 끄거나 줄이기 전까지 비용 증가 작업이 모두 막힌다.
- 한 작업(5행 단위) 안에서 같은 계정의 비용 행은 함께 검사한다. 그래서 하나가 걸리면 같은 계정의 다른 비용 행(입찰가 내리기 포함)도 막힌다(`bulk.safety_blocks`의 shortcut).

### ADVoost
- ADVoost는 네이버가 입찰가·검색어를 정한다. 그래서 클릭당 최대 입찰가를 적용할 수 없다.
- 이 앱은 ADVoost를 일반 수동입찰과 구분해 이렇게 처리한다.
  - **캠페인 하루예산 설정액이 있어야만** 켤 수 있다. 그 설정액도 실제 과금의 절대 상한은 아니라고 함께 안내한다.
  - 켜기는 늘 웹 승인 대상이다. 승인 화면에 "통제할 수 없는 항목"(`safety.ADVOOST_NOTE`)을 보여 준다.
- 캠페인 하루예산이 없으면 이유와 함께 막는다. 그 상태로 안전하게 운영할 방법을 확인하지 못했기 때문이다.

### 하루예산 설정액은 실제 과금 상한이 아니다
- 화면과 Claude에는 "하루예산 설정액"이라고만 쓴다. 모든 승인·미리보기에 `safety.OVERSPEND_NOTE`를 붙인다.
  - 반영 지연으로 더 과금될 수 있다.
  - 네이버 광고주센터에서 직접 바꾼 설정은 이 웹이 막을 수 없다.
- 근거: 네이버는 하루예산을 넘을 것으로 예상되면 광고를 '중지'로 바꾼다. 하지만 검색 결과에서 실제로 빠지기 전에 생긴 클릭은 과금될 수 있다.
  - 공식 원문 링크는 확인하지 못했다. 2차 출처: https://inside.ampm.co.kr/insight/3941 (2026-11-01 확인)
- 외부 변경은 막지 못하고, 실행 직전 재조회로만 반영한다. 승인 뒤 네이버 값이 바뀌었으면 실행하지 않는다(2절).

## 2. 웹 승인 (`approvals.py`, `approval_requests`)

### 흐름
1. **요청이 만들어지는 경우**
   - 대량 작업: 실행(`POST .../bulk-jobs/{id}/execute`, Claude `execute_job`)이나 예약(`.../schedule`, Claude `schedule_job`)을 했는데 웹 승인 대상 행이 있는 경우.
     - 서버는 실행하지 않고 승인 요청을 만들어 `approval`로 돌려준다.
     - 대상 판단: `bulk.needs_web_approval` → `safety.web_approval_needed`. 예산 증액인지는 네이버 지금 값으로 보고, 읽지 못하면 승인 대상으로 본다.
   - 플레이스: `place_ads_plan`(웹 `/place/plan`) 결과의 `summary.web_required`가 true인 경우. 이 요청은 `place_ads_apply`(`/place/apply`)로 실행되지 않는다(403과 승인 주소).
2. **승인:** 웹 `/approvals`의 `POST /workspaces/{ws}/approvals/{id}/approve`. 플레이스 화면의 승인 카드도 같은 API를 부른다. 승인하면 그 자리에서 실행한다. 예약 작업은 승인만 하고, 예약 시각에 크론이 실행한다.
3. **거절:** `.../reject`. 예약 작업이면 예약도 푼다.
4. **결과 확인:** 웹 `/approvals`(대기·최근 결과), Claude `get_approval`(읽기 전용).

### 막는 것
| 공격·실수 | 막는 곳 |
|---|---|
| Claude·MCP 토큰으로 승인 | 승인 API는 일반 API라 Claude 토큰을 거부한다(`access.user_from_header`, 401). 승인용 Claude 도구는 없다 |
| 승인 없이 실행 | `bulk.execute_job`이 처음 실행(PREVIEW) 때 승인(APPROVED/RUNNING)을 요구한다. 승인 없는 작업은 실행 묶음마다 계정 잠금 안에서 다시 판단해, 그사이 네이버 값이 바뀌어 '올리기'가 된 행을 막는다(`bulk._fail_web_rows`, 11/02 점검에서 찾은 우회). 웹·Claude·예약 크론 모두 같은 함수를 쓴다. 플레이스는 `place.apply`가 `web_required`를 거부한다 |
| 내용 변조 | 작업: 승인에 실행할 행의 해시(`bulk.job_hash`: 행 id·계정·대상·항목·전후 값)를 묶고, 승인할 때와 실행할 때 다시 계산한다. 플레이스: 정확한 변경 JSON의 해시이고, 실행은 저장된 payload만 쓴다 |
| 재사용 | 승인은 작업 하나·플레이스 계획 하나에 묶인다. PENDING→APPROVED/RUNNING을 UPDATE 한 문장으로 바꿔 한 번만 지나간다. 끝난 작업은 다시 실행할 수 없다(409) |
| 만료 | 대기 30분(`approvals.APPROVAL_TTL`, `place.WEB_APPROVAL_TTL`). 예약 작업은 예약 시각까지. 지나면 EXPIRED(410)이고, 다시 요청하면 새 승인 요청이 생긴다. 예약 시각을 바꾸거나 취소하면 전 승인은 EXPIRED |
| 다른 사용자·계정·조직 | 같은 조직 + 요청한 본인 또는 관리자 + 대상 계정을 모두 수정할 수 있는 사람만 승인할 수 있다. 다른 조직은 404 |
| 동시 중복 | 승인 claim은 UPDATE 한 문장, 행 실행은 VALID→RUNNING 한 문장, 비용 실행은 계정 잠금(3절) |
| 승인 뒤 네이버 값 변경 | 작업: 승인 요청을 만들 때 모든 변경 행(상태·입찰가·예산)의 변경 전 값을 **서버가 네이버에서 직접 읽어 저장**한다(`approvals._fill_before`). 화면·Claude가 보낸 값은 참고값(`claimed_before`, 다르면 승인 화면에 표시)일 뿐이다. 하나라도 읽지 못하거나 찾지 못하거나 의미를 판단할 수 없으면 승인 요청을 만들지 않고 이유를 돌려준다(400). 실행 때는 행마다 그 값(`expect`)과 네이버 지금 값을 비교해 다르면 실패한다(무제한 예산은 `무제한`으로 저장·비교). 플레이스: 승인 때 보여 준 "지금" 값과 실행 직전 값이 다르면 실패한다 |
| 승인 뒤 권한 회수 | 승인 API가 권한을 검사하고, 실행 직전에 행마다 다시 검사한다(`accessible_account_ids(edit=True)`). 예약은 크론 실행 시 작업을 만든 사람 권한으로 본다 |

### 상태·기록
- `approval_requests.status`: PENDING → (APPROVED: 예약 대기) → RUNNING → DONE·PARTIAL·FAILED, 또는 REJECTED·EXPIRED.
  - 작업의 최종 상태는 작업이 끝날 때 맞춘다(`bulk._finish_approval`). 플레이스는 `place._execute`의 `finish`가 맞춘다.
- 감사 로그 `APPROVAL_PENDING`·`APPROVAL_APPROVED`·`APPROVAL_DONE`·`APPROVAL_PARTIAL`·`APPROVAL_FAILED`·`APPROVAL_SUCCESS`(플레이스)·`APPROVAL_REJECTED`·`APPROVAL_EXPIRED`, 그리고 기존 `JOB_*`·행별 UPDATE/CREATE/DELETE.
- 승인 화면에 보여 준 내용은 `summary`(JSON)로 남긴다.
  - 작업: 광고 계정·대상·항목·전후 값(요약은 100행까지, 넘으면 승인 화면에서 "전체 N건 펼쳐 보기"로 작업의 모든 행을 불러오고, 펼치기 전에는 승인 버튼이 꺼져 있다)과 계정별 변경 후 합계·관리 기준·최대 입찰가·통제 불가 항목·과금 안내.
  - 플레이스: 대상·전후·지출 문구·안내.
- Claude에는 `execute_job`·`schedule_job`·`place_ads_plan` 결과의 `approval`·`approve_url`과 "승인 전에는 아무것도 바뀌지 않는다"는 문구를 돌려준다. 실제 결과는 `get_approval`로 구분해 전한다(MCP instructions).

### 플레이스 지출 문구 (`place._inspect`)
- `increases`: 이 변경으로 지출이 늘 수 있는지.
  - 예산 올리기, 입찰가 **올리기**, 켜기, ADVoost 켜기, 제외검색어 삭제만 true다.
- 문구
  - 늘지 않으면 "이 변경으로 지출이 늘지 않아요"
  - 늘 수 있고 캠페인 하루예산이 있으면 "지출이 늘 수 있어요. 캠페인 하루예산 설정액 …"
  - 늘 수 있는데 하루예산이 없으면 "… 하루 최대 지출을 정할 수 없어요"
  - 만들기는 "꺼진 상태로 만들어 지금은 지출이 없어요 …"
- 예전에는 하루예산 없는 캠페인의 입찰가 올리기에 "지출이 늘지 않아요"가 나왔다(11/02 고침).

### 웹 승인이 아닌 변경
- 입찰가·키워드/소재 켜기·등록·자동입찰은 지금처럼 Claude가 표를 보여 주고 허용 버튼으로 실행한다.
- 한계: Claude에서 "항상 허용"으로 두면 묻지 않고 실행된다. 서버의 안전장치·잠금은 그대로 적용된다.

### 긴급 중지
- `POST /workspaces/{ws}/stop`, Claude `stop_ad`.
- 승인·안전장치·계정 잠금 없이 바로 OFF로 바꾼다. 수정 권한은 필요하고 `EMERGENCY_STOP`을 기록한다.

## 3. 계정별 실행 잠금 (`safety.account_lock`, `account_locks`)

- 같은 광고 계정(조직이 달라도 같은 네이버 계정)의 비용 변경은 한 번에 하나만 "검사 → 네이버 반영"을 한다. 두 작업이 같은 옛 합계를 보고 함께 통과하지 않게 하기 위해서다.
- 얻기: `INSERT … ON CONFLICT DO UPDATE … WHERE expires_at < now` 한 문장. 쥔 열쇠(holder)가 내 것인지 다시 읽어 확인한다.
- 장애 복구: 임대 90초(`LOCK_LEASE`). 요청이 죽어 풀지 못한 잠금은 90초 뒤 다른 요청이 가져간다. 풀기는 내 열쇠일 때만 한다.
- 긴 실행: 비용 행을 네이버에 보내기 직전마다 내 잠금의 임대를 다시 90초로 연장한다(`safety.renew_lock`). 그사이 임대가 끝나 다른 요청이 가져갔으면 남은 비용 행은 실행하지 않는다(`safety.LOCK_LOST`). 재현 테스트: `test_lock_lease_renewed_and_lost_lock_stops`.
- 응답을 못 받은 쓰기(네트워크 오류·시간 초과)는 네이버에 반영됐을 수 있다. 행은 `bulk.UNKNOWN`(반영 여부 모름)으로 실패하고, 실패 행 재실행에서도 다시 실행하지 않는다(등록이 두 번 되지 않게). 플레이스도 같은 안내를 보여 준다. 자동 재시도는 어디에도 없다.
- 쓰는 곳
  - `bulk.execute_job`: 그 실행 묶음(최대 5행)에 비용 행이 있는 계정만 잠근다. 웹·Claude·예약·자동입찰·목표 ROAS가 모두 이곳을 지난다.
  - `place._execute`, `bulk.create_extension`.
- 잠금을 못 얻으면 비용 행은 FAILED이고 이유는 `safety.BUSY`다. 끄기 행은 그대로 실행한다. 자동으로 다시 시도하지 않는다. 실패 행 재실행으로 다시 한다.
- 한계: 네이버 호출 한 번이 90초를 넘기면(httpx 시간 제한 20초라 보통 없음) 그 한 건이 진행되는 동안 다른 요청이 잠금을 가져갈 수 있다. 네이버 쪽 반영 지연(합계 재조회가 방금 바꾼 값을 늦게 보여 주는 경우)은 확인하지 못했다.

## 4. 자동입찰·예약·목표 ROAS

- **자동입찰**
  - 규칙 저장이 범위 승인이다(Claude `set_auto_bid`도 허용 버튼). 웹 승인 대상은 아니다(사용자 결정).
  - 범위: 대상 계정·키워드, 기기·목표 순위, 최대 입찰가(≤ 계정 상한), 기간(`ends_on` ≤ 90일). 응답 `scope`와 웹 확인창에 변경 방식을 보여 준다.
  - 대상 추가·기간 연장·상한 올리기는 다시 저장해야 한다(`AUTO_BID_SET`). 중지는 언제든 할 수 있다.
  - 실행마다 확인하는 것: 만든 사람의 지금 수정 권한, 기간, 안전장치 설정, 입찰가 = min(규칙 최대, 계정 최대). 그다음 `execute_job`의 실제 입찰가·합계 검사와 잠금을 거친다. 그래서 **합계를 계산할 수 없는 계정에서는 입찰가를 올리지 않는다**(11/02부터).
- **예약 작업**
  - 예약할 때 안전장치를 검사하고, 웹 승인 대상이면 승인 요청을 만든다(만료 = 예약 시각).
  - 실행 때 승인·권한·변경 전 값·안전장치를 다시 확인하고, 조건이 다르면 실행하지 않는다. 결과는 행 FAILED와 이유, 작업 FAILED, `JOB_SCHEDULE_FAIL`, 승인 EXPIRED로 남는다.
  - 승인 없이 예약 시각이 되면 "웹 승인이 없어 실행하지 않음"으로 끝난다.
- **목표 ROAS**: 저장할 때 최대 입찰가 ≤ 계정 상한(미설정이면 거부). 실행(정책상 꺼져 있음)은 `execute_job` 검사를 거친다.

## 9. 실계정·운영에서 확인하지 못한 것, 남은 제한

1. 실계정 응답의 `useDailyBudget`·`sharedBudgetId`·`useGroupBidAmt`·쇼핑 소재 `adAttr` 모양, 브랜드검색 등 다른 캠페인 유형의 예산 필드. 없으면 무제한으로 보고 막는다.
2. 캠페인과 광고그룹 하루예산이 둘 다 있을 때 네이버가 어떻게 적용하는지. 지금은 캠페인 값만 센다.
3. ADVoost를 켠 뒤 실제 과금이 캠페인 하루예산 설정액을 얼마나 넘는지.
4. 운영 D1에서 0016 적용, 승인·잠금 동작, 쿠키 로그인을 직접 해 보지 않았다(로컬 SQLite 테스트만).
5. 계정 단위 함께 검사(1절 끝)와 실행 묶음 5행 때문에, 큰 작업은 앞 묶음이 반영된 뒤 다음 묶음을 검사한다. 묶음 사이에 다른 요청이 끼면 그때 상태로 다시 검사한다(통과를 보장하지 않음).
6. 웹 승인은 요청한 본인이나 관리자가 한다. 다른 사람의 결재(관리자 결재)는 없다(사용자 결정).
7. 예약 작업이 실행 시점에 막히면 작업 결과·승인 화면·대시보드에만 표시된다. 메일 같은 알림은 없다.
